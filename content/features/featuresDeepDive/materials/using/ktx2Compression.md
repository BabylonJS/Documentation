## Introduction

<img src="/img/resources/gpu_compressed_textures/compression_cesar.webp" title="Compression" caption="Photo credit : © Adam Rzepka - Centre Pompidou, MNAM-CCI /Dist. RMN-GP"/>

Using GPU compressed textures is becoming more and more important in the computer graphics / gaming world because it allows you to use more assets within the same memory budget and provides better performance by reducing cache misses on the GPU side.

Note that we are speaking about **GPU compressed textures**, meaning textures that remain compressed on the GPU. That's different from a `.png` or `.jpg` file, for example, which also holds compressed data but must be expanded before being sent to the GPU.

## Working with compressed texture formats

<img src="/img/resources/gpu_compressed_textures/container.webp" title="Container" caption="Photo courtesy of Depositphotos"/>

There are a number of compression formats used by the industry (ASTC, DXT, PVRTC, etc), and depending on your device it will generally support only a (small) subset of them : see [the table here](/features/featuresDeepDive/materials/advanced/mutliPlatTextures#khronos-texture-container-format--ktx-files) for more details. So, to support a wide range of devices, you would need to provide your assets in multiple different formats and Babylon.js would choose the right one depending on the capability of the target device.

It can be a bit tedious to generate and maintain so many formats for a given asset, so **container files** have been created. These files can either contain multiple formats of the same asset or be transcodable to multiple formats. Because this is the subject of this article, we are going to deal with the **KTX2 container file format**.

## KTX2 container

<img src="/img/resources/gpu_compressed_textures/ktx2.webp" title="KTX2"/>

**KTX** stands for **Khronos Texture Container** and the current incarnation is [v2.0](http://github.khronos.org/KTX-Specification/#basisu_gd) (we won't discuss version 1), and the associated file format extension is **.ktx2**.

This file does not in fact contain different formats of the same asset, but rather a **universal representation** of the data that can be transcoded to any format supported by the target device! We speak of **transcoding** instead of **expanding** because the data are not expanded per se; they are transformed into another compressed format, one supported by your target device (the universal representation is itself compressed).

Currently, the universal representation is generated by using a compression algorithm known as [Basis Universal](https://github.com/BinomialLLC/basis_universal#basis_universal), or **BasisU** for short, created by a company named Binomial. 

_Note_ : you may have already encountered or heard of **.basis** files. They use the same Basis compression scheme as `.ktx2` files, but the file format is not backed by any standards committee, unlike the KTX2 format. So, you should prefer the latter, as it will become the de-facto standard.

KTX2 files support two BasisU target formats :

- **ETC1S** : original low/medium quality mode, produces lower file sizes. Works best on images, photos, map data, or albedo/specular/etc. textures, but does not work as well on data that are not true color data (like normal maps, metallic/roughness maps, etc.)
- **UASTC** : high quality mode, can be used on any type of texture, even for non-color data maps

On top of this compression, the data can be further compressed in the UASTC case by using a [Zstandard](https://facebook.github.io/zstd/) compression scheme. Note, however, that this additional compression pass can lead to smaller `.ktx2` file sizes but not smaller GPU compressed textures! The data compressed with Zstandard will be expanded on the CPU side and then transcoded to a GPU texture.

Note that `.ktx2` files can also store GPU-compressed non-universal data, but as far as Babylon.js is concerned, it only deals with the ETC1S and UASTC universal compression schemes listed above.

## Babylon.js support for `.ktx2` files

<img src="/img/resources/gpu_compressed_textures/breeze.webp" title="KTX2" caption="Gif courtesy of giphy.com"/>

On the **Babylon.js** side, using such files is a breeze: just create a Texture instance that points to the `.ktx2` file you want to use, as you would with any other standard picture format (`png`, `jpg`, etc.)!

The KTX2 format is also used in the **glTF** world by means of the [KHR_texture_basisu extension](https://github.com/KhronosGroup/glTF/pull/1751) : this extension simply enables you to use .ktx2 files for the images used by your .gltf/.glb files and is supported by Babylon.js.


### Decoder package

The KTX2 implementation of Babylon.js is developed as an external package (the [KTX2 decoder](https://github.com/BabylonJS/Babylon.js/tree/master/ktx2Decoder)) designed to be small (the minified .js file is less than 22kb) and efficient. Depending on the universal representation of the data in the .ktx2 file and the compressed formats supported by the target device, the right module is used for the transcoding. Whenever possible, the [Universal Texture Transcoders](https://github.com/KhronosGroup/Universal-Texture-Transcoders) (UTT) are used, as they are both very fast and small. For transcoding formats not supported by the UTTs (yet), the [MSC Basis Transcoder](https://github.com/KhronosGroup/KTX-Software/releases) module is used instead.

Babylon.js wraps this package with `KhronosTextureContainer2`, which loads the required transcoders, manages workers, and selects an output format supported by the engine. The texture loader uses this wrapper automatically:

```javascript
const texture = new BABYLON.Texture("textures/texture.ktx2", scene);
```

Configure `KhronosTextureContainer2.URLConfig` and `DefaultNumWorkers` before loading your first KTX2 texture. See [self-hosting the decoder files](/setup/frameworkPackages/CDN) and [providing your own modules and workers](/setup/frameworkPackages/es6Support#ktx2-decoder-packages).

#### Options

Pass decoder options through `loaderOptions` when creating a texture:

```javascript
const texture = new BABYLON.Texture("textures/texture.ktx2", scene, {
    loaderOptions: {
        forceRGBA: true,
    },
});
```

- Use `forceRGBA: true` to decode to uncompressed RGBA instead of a GPU-compressed format.
- For UASTC textures, use `forceR8: true` or `forceRG8: true` to keep just the red channel or the red and green channels.
- Use `useRGBAIfASTCBC7NotAvailableWhenUASTC: true` to decode UASTC to RGBA when neither ASTC nor BC7 is supported.
- Use `bypassTranscoders` to exclude specific transcoders by name.

Set properties on `KhronosTextureContainer2.DefaultDecoderOptions` to override per-texture options. By default, `useRGBAIfOnlyBC1BC3AvailableWhenUASTC` is `true`: the decoder favors faster RGBA decoding over slower UASTC-to-BC1/BC3 transcoding. To favor compressed textures on those devices instead:

```javascript
BABYLON.KhronosTextureContainer2.DefaultDecoderOptions.useRGBAIfOnlyBC1BC3AvailableWhenUASTC = false;
```

### Encoder package

The complementary `@babylonjs/ktx2encoder` package converts pixels into `.ktx2` files.

**Package availability:** As of October 29, 2026, the public npm registry's `latest` endpoint for `@babylonjs/ktx2encoder` returns HTTP 404. The package-based examples below require a published package; merging the encoder does not make an npm release available. Use the [external tools](#tools) until the package is available.

```javascript
import { KTX2Encoder } from "@babylonjs/ktx2encoder";

const encoder = new KTX2Encoder();
const rgba = new Uint8Array(4 * 4 * 4).fill(255); // A white 4 x 4 image.
const ktx2 = await encoder.encode(rgba, 4, 4, { usage: "color" }); // Returns Uint8Array containing the KTX2 file
```
#### Options

- Supply top-down RGBA8 pixels with exactly `width * height * 4` bytes. 
- Width and height must each be a multiple of 4 from 4 through 16,384 pixels, with at most 12,582,912 pixels in total.
- Choose `usage: "color"` for color textures, which uses ETC1S
- Choose `usage: "data"` for metallic/roughness maps, or `"normal"` for normal maps. 
- Pass `flipY: true` for bottom-up pixels (default `false`)
- Pass `generateMipmaps: false` to skip mipmap generation (default `true`). Each call releases its native encoder; the standalone instance has no `dispose()` method. Once `encode()` starts, it cannot be cancelled.

Set `KTX2Encoder.DefaultEncoderOptions` to force codec settings for every later `encode()` call. As with the KTX2 decoder's default options, a defined default overrides the value passed to `encode()`.

`DefaultEncoderOptions` starts empty. These are the built-in codec values, shown as explicit overrides:

```javascript
KTX2Encoder.DefaultEncoderOptions = {
    etc1sQualityLevel: 128,
    etc1sCompressionLevel: 2,
    uastcQualityLevel: 2,
    zstandard: true,
};
```

Note that a default applies only where it is relevant: the ETC1S settings to `"color"`, and the UASTC settings to `"data"` and `"normal"`. 

## Tools

<img src="/img/resources/gpu_compressed_textures/tools.webp" title="Tools" caption="Photo courtesy of pixels.com"/>

Now that you know why you should use `.ktx2` files, you will need to actually generate them!

The [encoder package](#encoder-package) above can generate KTX2 files from pixel data, but it is still experimental. For other ways to create them in the meantime, see the tools below.

Khronos provides [command line tools](https://github.com/KhronosGroup/KTX-Software/releases) that you can use to generate, check, and dump `.ktx2` files:

- **toktx.exe** is the primary tool, used to generate .ktx2 files from .png, .jpg files. There are a handful of options, just type **toktx.exe** to display them
- **ktxinfo.exe** will display useful data in human readable form about a .ktx2 file
- **ktx2check.exe** will check that your .ktx2 file is a valid file
- **ktxsc.exe** will allow you to update some parameters of an existing .ktx2 file (change the compression scheme, add a Zstandard compression, etc)
